# Frontend

> Describes the current code. The reasons are in [0004](../decisions/0004-react-spa.md) and
> [0005](../decisions/0005-ui-design-system.md).

## Stack

| Concern | Choice |
|---|---|
| Language and build | TypeScript, Vite (built into `backend/public/app`, served at `/app`) |
| Routing | React Router; the admin routes and the statistics each load as a separate bundle, and a player's page and the results screen load their charts as one |
| Server data | TanStack Query (`src/api/queries.ts`) |
| API client and types | `openapi-fetch` with types generated by `openapi-typescript` from `openapi.json` |
| Forms | React state with React Aria `Form`; field errors come from the API. React Hook Form and Zod (planned in 0004) were not needed yet |
| Components | React Aria Components, styled with Tailwind and `tailwindcss-react-aria-components` (state variants such as `selected:` and `pressed:`) |
| Design tokens | CSS variables in `src/tokens/tokens.css`, owned by the designer |
| Charts | Recharts, only in `src/features/statistics` ([0015](../decisions/0015-chart-library.md)): colors from the `chart-1` to `chart-8` tokens ([0020](../decisions/0020-eight-chart-colors.md)), a table of the same numbers under each chart |
| Component workshop | Storybook, with the API mocked by MSW (`src/mocks`). It is not published with the site |
| Tests | Vitest (units), Playwright (end to end, phone and desktop), axe (accessibility) |
| Install | PWA manifest with PNG icons and a minimal service worker (no offline data); see [Installing on a phone](#installing-on-a-phone) |

## Site settings

A site's name, logo, language, money, time zone and main color are in its site folder's `site.json`
([`site/README.md`](../../site/README.md)). The folder is `../site`, the demo site, unless `PTSITE_SITE_DIR`
names another one. The frontend reads it **when it is built**, so the page, the installed app and the login
screen have the right name and colors before the first request to the API.

- **`site-settings.ts`** reads and checks the file. A wrong setting stops the build with a plain message.
  `vite.config.ts` puts the result in the constant `__SITE__`; code reads it through `src/lib/site.ts`, never
  directly.
- **Its Vite plugin** writes the page's title, language and theme color into `index.html`, makes
  `manifest.webmanifest` and `favicon.svg`, adds the site's `theme.css`, and puts the files of the site's
  `public/` folder over the frontend's own. `PTSITE_OUT_DIR` sends the build to a site's own backend.
- **The main color** is one value, `brandColor`. `src/site/brand.ts` makes the hover, soft and current-month
  shades from it, and the plugin writes them after `tokens.css`. The build stops when text on the color, or
  the color as text, has a contrast below 4.5:1. A site changes any other token in its `theme.css`.
- **Formats.** `src/lib/format.ts` and `src/lib/dates.ts` build every `Intl` formatter from `site.locale`,
  `site.currency` and `site.timeZone`. No component names a language, a currency or a time zone.
- **The icons** are drawn on the main color by `npm run icons`, into the site folder's `public/icons` when
  `PTSITE_SITE_DIR` is set.
- The unit tests, Storybook and the end-to-end tests run on the demo site.

### Feature flags

A site turns a part of the product off in `features` of its `site.json`
([0021](../decisions/0021-feature-flags.md); the list is in [`site/README.md`](../../site/README.md)).

- **`src/site/features.ts`** has every flag with its default. `site-settings.ts` checks the site's `features`
  against it and stops the build on a name it does not know.
- **A screen asks `hasFeature('timeChip')`** of `src/lib/features.ts`, and leaves out the field, the row or the
  link when the answer is no. Hiding is cosmetic: the API refuses the feature too.
- **The demo site has every feature**, the Main Event, the house owner's buy-in and the night dashboard too, which it turns on in `site/site.json`. So a test or a story shows the other way with `overrideFeatures` (a test)
  or the decorator `withFeatures` of `src/mocks/withFeatures.tsx` (a story).
- **"Configurações" in "Administração" lists every flag** with whether the site has it (`SettingsAdmin`). Each
  flag has a name and a description in `t.admin.settings.features`. It reads the bundle, as every screen does.
- To add a flag, follow "Adding a feature flag" in [backend-layers.md](backend-layers.md).

## Texts

Every text a visitor reads or hears is in `src/i18n`, never in a component. This is what lets the site run in
another language and lets a site reword a text.

- **One file per area and per language:** `src/i18n/pt-BR/nights.ts`, `src/i18n/en/nights.ts`. `common.ts` has
  the words used in more than one area.
- **Brazilian Portuguese is the reference.** The shape of its objects is the type `Messages`. Each English file
  has that type, so a missing or misspelled key fails `npx tsc -b`.
- **A text is a string, or a function of one object of named values** when it has a value in it:
  `t.nights.title({ date })`. A text with a plural uses `plural()` (`src/i18n/plural.ts`), which follows the
  site's language.
- **A sentence with an element in it stays one text**, with the element's place in braces, and is drawn with
  `rich()`: `rich(t.auth.forgot.sent, { email: <strong>{email}</strong> })`. A translator can then move the
  name to where the language wants it.
- **The site's language picks the catalogue** when the app starts (`site.locale`): Portuguese for `pt…`,
  English for anything else. Dates, numbers and money follow `site.locale` itself (see "Site settings").
- **A site rewords single texts** in `messages.json` of its site folder: the same shape as the catalogue, with
  only the texts it changes, as strings. A text with values names them in braces: `"Pote ME ({currency})"`. A
  name that is not in the catalogue stops the app when it starts, with the name in the message.
- **Code reads a text as `t.<area>.<name>`** (`import { t } from '@/i18n'`). Formats stay in `src/lib/format.ts`.
- **`scripts/check-i18n.mjs`, part of `npm run lint`,** fails when a file outside `src/i18n` writes a text of
  its own. Tests, stories and `src/mocks` are not checked: they name the texts they expect, in the demo site's
  language.

To add a text: add the key to the area's file in `pt-BR/`, add it to the same file in `en/`, and use it.

The API's messages are translated in the backend the same way: `backend/lang/pt_BR` and `backend/lang/en`
(`rules.php`, `mail.php`, `auth.php`, `validation.php`). A site rewords one in its own `backend/lang` folder.

## Selected season

The standings, results, calendar, simulator, statistics (`/statistics`) and a player's page (`/players/:id`) show
one season, the **selected season**
([seasons-and-nights.md](../specs/seasons-and-nights.md) rules 3a to 3f).

The address says which season: `/results` is the current season and `/seasons/7/results` is season 7.

- `src/routes.tsx` mounts one list of season screens twice: at the root and under `seasons/:seasonId`. So both
  addresses render the same components.
- `src/lib/seasonPath.ts` has the address helpers: `splitSeasonPath()` and `seasonPath()` take an address apart and
  build one, `isSeasonScreen()` tells whether a path is a season screen, and `useSeasonPath()` returns the
  function that makes a link keep the season on screen (`to('/results')`). A new season screen needs a line in
  its list and a route.
- `useSelectedSeason()` (`features/layout`) returns the season to show, from the address. Screens never read the
  id themselves. A season that answers 404 or is archived is replaced by the same screen of the current season.
  `usePathOfSeason()`, next to it, builds the address of a given season, for a link that leaves a night or the
  admin section.
- `src/lib/selectedSeason.ts` keeps the id of the last season shown in the browser's `sessionStorage`, so it lasts
  until the browser tab closes. `AppLayout` writes it on every season screen. Only the screens with no season of
  their own read it, for their header and their menu. The address with no season stores none, so the site follows
  a newly opened season. `useLogout` clears it.
- The header shows the selected season's name as a link to `/seasons/select`. `SeasonNotice` appears on the
  season screens while the season is not the current one; "Voltar para a atual" opens the same screen at the
  address with no season.
- `usePickSeason()` (`features/seasons`) opens a season's address. "Escolher temporada" and "Temporadas" both use
  it.

## Navigation

`features/layout/navigation.ts` lists every place of the site once. A new item is one line there.

- **Menu:** the "Menu" button in the header opens a left drawer (`NavDrawer`) with every item, the user's name
  and "Sair", on phones and on desktop.
- **Phones:** the bottom tab bar holds the items marked `tab`, five at most. "Sair" is only in the menu.
- **Desktop:** the top bar holds the items marked `top`.
- **"Simulação" and "Main Event" are only in the menu.** The standings also link to the simulator.

## Footer

Every page ends with `SiteFooter` (`features/layout/SiteFooter.tsx`), which shows the site's version, for example
"Liga Demo v2.1.0". No single layout wraps every route, so the footer is in each of the four page frames:
`AppLayout`, `AuthShell` (the screens before login), `BareLayout` and `ErrorPage`. A new frame must add it too.

`BareLayout` (`features/layout/BareLayout.tsx`) is the frame of a screen that fills the phone, with no header and
no menus: the night dashboard. It sends a visitor who is not logged in to the login page, as `AppLayout` does.
Its screen has its own way back to the site.

The version is the constant `__APP_VERSION__`, set at build time in `vite.config.ts` and declared in
`src/vite-env.d.ts`. Where it comes from: [deployment.md](deployment.md), "Releases".

"Configurações" in "Administração" shows the same version. A site's build has two, joined as
"v3.0.0+ptsite.v1.8.0", and `splitVersion()` (`src/lib/version.ts`) shows them on two lines: the site's and the
core's.

## Desktop layout

The same screens adapt from 640px wide (Tailwind's `sm`) upwards. No feature is desktop-only: a shortcut shown
only on desktop also exists on another screen.

- **Navigation:** the bottom tab bar on phones becomes links in the top bar, which also has "Estatísticas",
  "Temporadas", "Administração" (admins) and "Sair". "Meu perfil" is the last item before "Administração".
- **Width:** content is centred with a maximum width of 1024px (`max-w-5xl`).
- **Standings:** the table gains the "Pontuou" and "Vitórias" columns, and the last result and simulator link
  move to a side column (from 1024px, `lg`).
- **Results:** night cards sit in a grid of two, then three columns.
- **Forms:** short fields sit side by side (scheduling: suggestions in a row, then date, time and place); the
  results form keeps one column, at most 576px wide, and its submit bar is no longer pinned to the bottom.
- **Admin players:** each row of the list gains "Inativar" / "Ativar" and "Arquivar" / "Restaurar". On phones
  these buttons are only on the player's own page.
- **Dialogs:** the player picker and confirmations open as centred dialogs instead of bottom sheets.

## Archiving

- **Every "Arquivar" asks first**, with `ConfirmDialog` (`src/components/ConfirmDialog.tsx`): players, places,
  holidays and "Cancelar evento". The dialog names the record and says what stops showing.
- **"Restaurar" takes effect at once**, like "Inativar" / "Ativar". It hides nothing, and one more click undoes it.
- **The admin lists show archived records**, struck through with an "arquivado" badge and a "Restaurar" button:
  players, places and the holiday table. They ask the API for them with `archived=1`. The place pickers do not,
  and the filter is part of the query key, so they never get archived places from the cache.

## Rules

- **Mobile first.** Design at phone width first. On phones, the main navigation is a bottom tab bar, and forms
  use one column with touch targets of at least 44px (`min-h-touch`).
- **Pickers open as sheets.** Choosing a player opens a full-screen sheet with search (`PlayerPicker`). A
  dropdown closed when the phone keyboard scrolled the page. The "add a new player" row comes after the
  matching players, so tapping the first row never creates a player by accident.
- **Tokens only.** Components never use raw colors, sizes or fonts. Tailwind's default palette is switched off
  in `tokens.css`, so only token classes exist.
- **Striped rows.** The body rows of a data table, and the lines of a list that reads as one (finishing
  positions, the admin lists, the audit log, the seasons list), use
  `even:bg-surface-stripe`. The first and last cell have side padding, so the text does not touch the stripe's
  edge.
- **One tap, one change, on the night dashboard.** A mark is a chip that one tap turns on or off (`ToggleChip`),
  saved at once with no "Salvar" (only the amounts typed by hand have one). A buy-in and a rebuy have one state
  more, for a payment that was not in cash: a second tap sets it, with the sign ⇄ in place of the check mark,
  and a third unmarks the payment. Its chips are 36px high, smaller
  than the 44px of the rest of the site, so that a player's row fits a phone. The screen shows the change before the API answers
  (`features/dashboard/dashboardMoney.ts` has the API's rules for it) and puts it back if the API refuses. The
  changes of a night are sent one at a time, in order.
- **Only the night dashboard refreshes by itself.** It asks the API again every 10 seconds while it is on screen
  ([0022](../decisions/0022-polling-for-the-night-dashboard.md)). Every other screen is read again when the
  window gets the focus back.
- **The API decides.** Screens show the API's messages. Permissions come from `GET /me` `abilities`; hiding an
  action is cosmetic.
- **Every component and screen state has a story.** Empty, loading, error, long text, phone width.
- **Accessibility:** WCAG 2.2 AA. axe runs on every story and in every end-to-end test; failures fail CI.
- **Language:** screens in Brazilian Portuguese (pt-BR) with pt-BR money, number and date formats. Code and
  URL paths in English.

## Commands

```sh
npm run dev              # Vite on :5173, proxying /api and /sanctum to Laravel on :8000
npm run build            # into backend/public/app
npm test                 # unit tests
npm run storybook        # Storybook on :6006
npm run test:e2e         # Playwright; starts its own Laravel servers with fresh databases
npm run test:e2e:parallel # the same tests, phone and desktop at the same time, as CI runs them
npm run build-storybook && npm run test:storybook   # every story renders and passes axe
npm run api:types        # after the backend's API changes
npm run screenshots      # phone screenshots into docs/screens
npm run icons            # the app icons in public/icons, from public/favicon.svg
```

The ports are in `ports.ts`. A port offset moves them all, so two git worktrees can run servers and tests at
the same time. The offset comes from `local/ports.env`, which `task worktree:init` writes in a new worktree, or
else from the `PORT_OFFSET` environment variable; without either it is 0. The screenshot script and
`Taskfile.yml` read it the same way. `npm run storybook` is the exception: it always uses `:6006`, and
`task storybook` uses the moved port.

In a container with a preinstalled Chromium, set `PW_CHROMIUM_PATH` to its path for the Playwright commands.

Each end-to-end server (`scripts/e2e-server.mjs`) seeds a fresh MySQL database of its own (see
[Development database](overview.md#development-database)) with the demo league and the development logins, then adds the test seasons from `backend/database/seeders/EndToEndSeeder.php` (named
"E2E …"). Tests that schedule, open or plan nights use those seasons, not the demo league's, so a change to the demo
data does not break them. Tests that only read, such as standings and the calendar, use the demo league.

## Installing on a phone

The site is a PWA (progressive web app): a phone can install it from the browser, and it then opens from its
own icon, full screen, without the browser bar. It is the same site and still needs a connection.

- **Chrome on a phone:** open the site, then the browser menu, then "Adicionar à tela inicial" and "Instalar".
- **iPhone (Safari):** the share button, then "Adicionar à Tela de Início".

Chrome offers the install only when all of these hold:

- the site is served over HTTPS;
- `public/manifest.webmanifest` has a name, `display: standalone` and PNG icons of 192 and 512 pixels;
- a service worker is registered (`public/sw.js`, registered in `src/main.tsx` in production builds only).

The icons in `public/icons` are made from `public/favicon.svg` by `npm run icons` (`scripts/make-icons.mjs`)
and committed. Run it again when the logo changes. The "maskable" icon and the iPhone icon have no transparent
corners, because the phone cuts them to its own shape. `src/manifest.test.ts` checks that the manifest and the
icon files agree.

`backend/public/.htaccess` gives `.webmanifest` its content type (`application/manifest+json`), which the
shared host does not know.
